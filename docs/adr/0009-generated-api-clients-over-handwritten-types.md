# ADR-0009 — Generated API clients; hand-written types are hardcoding

**Status:** Accepted — 2026-07-29
**Deciders:** Platform architecture
**Related:** ADR-0003 (metadata-driven), ADR-0011 (Flutter), ADR-0012 (Next.js)

---

## Context

North Star §3 states it flatly: *"API types: Generated from OpenAPI. Hand-written types are
hardcoding. Types drift = bugs."* Four clients consume the API — customer web, dealer web, admin
web, and three Flutter apps sharing one Dart client. Every one of them needs the same request
shapes, response shapes, error codes and permission strings.

The failure modes, both of which are ordinary and both of which have cost real money:

> **The silent field drop.** The backend adds `tcs_minor` to the deal price breakdown for sales above
> ₹10 lakh. The Flutter app's hand-written `PriceBreakdown` model has a fixed `fromJson` that ignores
> unknown keys. Buyers on Android see a total that is ₹8,400 lower than what they are asked to pay at
> checkout. Nobody notices for eleven days because the web app was updated by the same dev who wrote
> the backend, and the Android dev was on another feature.

> **The frozen union.** A frontend dev types `status: 'draft' | 'live' | 'sold'` because that is what
> the API returned in March. In July the Workflow Registry gains `LEGAL_HOLD` — **without a deploy**,
> which is the entire point of ADR-0004 — and the dealer portal renders a blank status pill and
> throws in a `switch` that had an exhaustive-check `never` branch. The registry did its job; the
> hand-written type destroyed the benefit.

The second one is the important one. In a metadata-driven platform, **a hand-written enum in a client
is not merely duplication — it is a hardcoding of registry data on the far side of a network
boundary, where the registry cannot reach it.**

## Decision

**The server's OpenAPI document is the contract. All client types, validators, hooks and error
unions are generated from it and committed. Registry-driven values are never emitted as static
enums.**

### 1. Document production

ASP.NET Core 9 `Microsoft.AspNetCore.OpenApi`, one document per major version, served at
`/openapi/v1.json` and written to `packages/api/openapi/v1.json` at build time via
`Microsoft.Extensions.ApiDescription.Server`.

A document transformer attaches AutoHub extensions to every operation:

| Extension | Meaning |
|---|---|
| `x-ah-permission`, `x-ah-scope` | RBAC requirement, resolved from the handler's guard |
| `x-ah-idempotent` | Whether `Idempotency-Key` is required |
| `x-ah-rate-limit-bucket` | Which limiter applies |
| `x-ah-stability` | `stable` \| `experimental` \| `deprecated` |
| `x-ah-error-codes` | The operation's full failure-code set |
| `x-ah-enum-source` | For registry-driven string fields |

**`x-ah-error-codes` is generated by a Roslyn source generator that walks the handler's actual
`Result` failure paths** — not from an attribute someone remembers to add. Drift between what the
code can return and what the contract says becomes impossible rather than merely discouraged. That
single decision is what makes the generated error unions trustworthy enough to `switch` on.

### 2. The Prime Directive clause

Registry-driven values are **`type: string` with `x-ah-enum-source`**, never an OpenAPI `enum`:

```jsonc
"state_key": { "type": "string", "x-ah-enum-source": "workflow:listing.sale.c2c:states" }
"fuel_type": { "type": "string", "x-ah-enum-source": "taxonomy:attr:fuel_type" }
"permission": { "type": "string", "x-ah-enum-source": "rbac:permissions" }
```

Emitting these as enums would bake registry data into generated client code and break every deployed
client the moment someone adds a fuel type. The client instead fetches the option set from the
registry endpoints at runtime and caches it against `X-AutoHub-Registry-Version`.

Dynamic form payloads are `additionalProperties: true`. A listing's `attributes` is
`Record<string, unknown>` in TypeScript, narrowed at runtime by `packages/forms` from the Form Schema
Registry. **Generating a static type for a dynamic form is exactly the hardcoding this platform
exists to avoid.**

Error codes and permission strings, by contrast, **are** code artefacts (they change with a deploy),
so they are generated as exhaustive unions.

### 3. Generation topology

```
packages/api/openapi/v1.json
   ├─ orval             → packages/api/src/generated/{schemas,zod,hooks}.ts
   ├─ custom generator  → packages/api/src/generated/{error-codes,permissions}.ts
   └─ openapi-generator → mobile/packages/autohub_api  (dart-dio, freezed)
```

Both generators run in the **same CI job**, so web and mobile can never be generated from different
document versions. Output is **committed and CI-verified** (`git diff --exit-code` after
regeneration) — reviewers see contract changes as a diff in the PR, which is the entire point.

### 4. The fetcher is generated infrastructure, not per-app code

One `fetcher` in `packages/api` (and one `AutoHubClient` in Dart with identical rules) implements
every client behaviour the API contract mandates, exactly once:

- injects `Authorization`, `Idempotency-Key` (auto-generated per mutation, **stable across retries**),
  `X-AutoHub-Device-Id`, `X-AutoHub-Client`, `Accept-Language`, `X-AutoHub-Scope`
- unwraps the `Result<T>` envelope; converts RFC 9457 `problem+json` into a typed `ApiError`
- retries `429`/`503`/network with full jitter, honouring `Retry-After`
- compares `X-AutoHub-Registry-Version` against the cached registry epoch and **invalidates drifted
  TanStack Query keys** — the mechanism by which a registry change propagates to a live browser tab

Zod policy: **requests `.strict()`, responses `.passthrough()`**. A typo'd request field fails loudly;
an additive server change never breaks a deployed client. Runtime response validation is
dev/staging only — full Zod parsing of a 100-item search response on a mid-range Android device
costs real milliseconds, and production trusts the CI gates instead.

### 5. CI gates

| Gate | Tool | Fails on |
|---|---|---|
| Lint | Spectral + AutoHub ruleset | Missing `operationId`/`x-ah-permission`, non-kebab path, missing 401/429 responses |
| Breaking change | `oasdiff breaking` vs `main` | Any breaking change without `x-ah-stability: experimental` or an approved `BREAKING-CHANGE:` trailer |
| Error-code coverage | custom | A code in `ErrorCodes.cs` no operation declares, or vice versa |
| Enum-source lint | custom | An OpenAPI `enum` on a field whose values come from a registry — **the Prime Directive gate** |
| Example validity | `openapi-examples-validator` | Examples that fail their own schema |
| Client drift | `git diff --exit-code` | Committed client out of sync with the document |

## Consequences

**Positive**

- A backend field addition appears in TS types, Zod schemas, TanStack hooks and Dart models in one
  CI run. The silent-field-drop incident becomes structurally impossible.
- Error handling is exhaustively typed *per operation*: `if (error?.code === 'auction.bid.below_increment')`
  narrows to that operation's declared code union, and `error.errors[0].params.min_next_minor` is
  typed as a number.
- Breaking changes are caught by `oasdiff` at PR time rather than by a mobile crash report a week
  after the store release.
- Cross-platform parity is enforced by construction — one document, one CI job, two generators.
- The contract is reviewable. The `v1.json` diff in a PR is the honest summary of what changed.

**Negative — stated honestly**

- **Generated diffs are enormous.** A one-field change can produce a 400-line diff across four files.
  Mitigation: generated output lands in its **own commit** with a `chore(api):` prefix, `CODEOWNERS`
  routes it to the platform team, and reviewers read `v1.json` rather than the emitted code.
- **You inherit the generator's bugs.** orval and openapi-generator both have sharp edges (oneOf
  handling, nullable semantics, `additionalProperties`). Mitigation: generator versions are pinned
  exactly, upgrades are their own PR with a full regenerate + diff review, and we keep a small
  `overrides/` layer for known-bad output rather than hand-editing generated files.
- **Bundle size.** A single generated client for 300 operations is large. Mitigation: per-module
  entrypoints (`@autohub/api/listings`, `@autohub/api/auction`) so tree-shaking works, and the admin
  app — which needs everything — accepts the weight because it is not SEO- or 3G-sensitive.
- **The contract must actually be accurate.** Generated types are worse than hand-written ones if the
  document lies. The Roslyn error-code generator and the coverage gate exist because a
  hand-maintained `x-ah-error-codes` would be wrong within a month.
- **Two-step workflow.** Backend change → regenerate → frontend change. Local DX mitigations: a
  `pnpm api:gen` watcher against the dev server, and the ability to point the generator at a local
  branch's document.
- **`Record<string, unknown>` for dynamic attributes is genuinely less safe** than a static type, and
  that is a deliberate trade. The safety comes back at runtime from the Form Schema validator — but
  only for code that goes through it. Direct `listing.attributes['fuel_type']` access is unchecked;
  an ESLint rule pushes consumers to the typed accessor from `packages/forms`.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| **Hand-written types in a shared `@autohub/types` package** | Drift is a matter of when, not if, and it drifts silently. Also does nothing for Flutter (Dart cannot consume a TS package), so it would be hand-written twice. |
| **tRPC** | Excellent end-to-end inference — for a TypeScript backend. Our backend is ASP.NET Core 9 (North Star §3). Non-starter. |
| **GraphQL + codegen** | Solves over-fetching and gives great codegen. Rejected: North Star §3 explicitly defers GraphQL; registry-driven dynamic attributes fit GraphQL's static schema *worse* than OpenAPI's `additionalProperties`; and per-field authorization against a scoped RBAC registry plus N+1 control is a large amount of machinery for a problem (payload size) we can solve with sparse fieldsets. |
| **gRPC / protobuf** | Best type story of any option. Rejected on browser support (grpc-web proxy), on tooling ergonomics for a REST-shaped public surface, and because OpenAPI is the lingua franca for the third-party integrations (dealers, lenders, insurers) that will consume this API in Phase 6. |
| **Client-first contract** (write the OpenAPI by hand, implement to it) | Design-first is defensible and produces cleaner APIs. Rejected because a hand-maintained document drifts from the implementation exactly as badly as hand-written types drift from the API — and the Roslyn-generated error codes are only possible when the code is the source. Design review happens on the `v1.json` diff instead. |
| **Runtime response validation in production** | Would catch drift in the field. Rejected on cost: parsing a large search response with Zod on a mid-range Android device is measurable, and the CI gates already prevent the drift it would catch. Enabled in dev/staging, and behind a Feature Registry flag for a 1% production sample if we ever need evidence. |

## Revisit when

1. `oasdiff` reports **zero** breaking changes for two consecutive quarters while client bug reports
   about payload shape continue — that means the document is lying and the generator pipeline needs
   auditing, not extending.
2. The generated TS client exceeds **~150 KB gzipped** in the customer app's critical path — split
   further, or move the customer app to a hand-curated subset generated from a filtered document.
3. A third-party partner integration (lender, insurer) needs a **stable, narrower public API** — then
   emit a second OpenAPI document (`/openapi/partner-v1.json`) from a tagged subset, with its own
   stability guarantees. Do not let partner needs deform the internal contract.
4. We adopt a second backend language for a Phase 7 ML service — the document stays the boundary, and
   that service publishes its own document into the same generation pipeline.
5. `x-ah-enum-source` fields start being `switch`ed on in client code anyway (detectable by an ESLint
   rule) — that is the Prime Directive leaking, and the fix is better registry-option hooks, not
   static enums.
